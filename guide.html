On-premises provisioning: Privileged or Unprivileged

With on-premises providers, YugabyteDB Anywhere (YBA) does not create VMs. You create the VMs and install a supported Linux OS, then add them to the provider’s free pool of nodes. Whether a node must be provisioned before you add it depends on the provisioning mode.

Will you give YBA an SSH user with passwordless sudo on your database nodes?

Manually Provision Nodes is OFF

Privileged. Yes, YBA gets sudo. You add bare VMs and YBA provisions them over SSH, including OS-level settings.

Unprivileged. No, YBA never gets sudo. Your system administrator runs node-agent-provision.sh on each node first; the script also adds the node to the free pool.

If you are unsure, start from your organization’s security policy. If granting root-equivalent access to YBA is not allowed, use Unprivileged provisioning.

Set up Privileged provisioning

YBA connects to each node over SSH as a user with passwordless sudo and performs all OS-level provisioning itself. After the VMs exist, you typically do not need to run anything on the nodes.

  1. Open the network. Have your network administrator open the ports YBA and the nodes need to communicate. See Networking.
  2. Create the VMs. Place them in the regions and availability zones where you will deploy universes, install a YugabyteDB-supported Linux OS, and create an SSH user with passwordless sudo on every VM (for example, ec2-user on AWS EC2). See Privileged provisioning requirements.
  3. Create the provider in YBA. Define regions and availability zones, provide the SSH credentials for the sudo-capable user, provide the NTP setup, and leave Manually Provision Nodes OFF. See Create the provider configuration.
  4. Define instance types. An instance type describes basic properties of the VMs you will add.
  5. Add the VMs to the provider. YBA provisions each VM automatically using the sudo-capable SSH user.
  6. Run pre-checks to validate the nodes. See Add nodes to the on-premises provider.
Turning on Manually Provision Nodes changes the mode. The provider becomes Unprivileged: YBA stops provisioning nodes, and each node must be prepared with node-agent-provision.sh before you add it.

Set up Unprivileged provisioning

YBA has no sudo access to your nodes. Your system administrator prepares each node with the node-agent-provision.sh script, which provisions the VM, installs node agent, creates the on-premises provider, and adds the node to its free pool.

Root or sudo is needed only while the script runs. After the node is provisioned and node agent is installed, sudo is no longer required.

Before you start

  • One, three, five, or more VMs with a supported Linux OS and the additional software installed. For nodes without internet access, also install the airgapped software.
  • YBA installed and running, so the script can create the provider and register the node.
  • The VMs are reachable from YBA on ports 9070 and 443. See Networking requirements.
  • Data directories or mount points created on each node, typically /data, or /mnt/d0, /mnt/d1, and so on for multiple drives. The yugabyte user that the script creates must be able to access them.

Set up the provider

An Unprivileged provider is an on-premises provider with Manually Provision Nodes ON and no SSH key pair. The provisioning script creates it for you; you don’t create it in the YBA UI.

Fill in the YBA connection and provider details in node-agent-provision.yaml (step 2 below). The first node you provision creates the provider with Manually Provision Nodes ON, along with its region, zone and instance type. Each later node that uses the same provider name is added to that provider.

Provision each node

  1. Download the node agent package to the VM. If YBA is running, download it with the API. This works without internet access and gets the node agent version that matches your YBA. 
    curl -k https://<yba_address>/api/v1/node_agents/download\?downloadType\=package\&os\=LINUX\&arch\=AMD64 --fail --header 'X-AUTH-YW-API-TOKEN: <api_token>' > node-agent.tar.gz
tar -xvzf node-agent.tar.gz && cd 2026.1.2.0-b137/scripts/

    Replace <yba_address> with your YBA address and <api_token> with an API token from a user with the Admin role or higher. Use ARM64 instead of AMD64 on ARM nodes, and use the version directory from your package.

    Download from the YBA Installer package instead 
    wget https://downloads.yugabyte.com/releases/2026.1.2.0/yba_installer_full-2026.1.2.0-b137-linux-x86_64.tar.gz
tar -xf yba_installer_full-2026.1.2.0-b137-linux-x86_64.tar.gz
cd yba_installer_full-2026.1.2.0-b137/
tar -xf yugabundle-2026.1.2.0-b137-centos-x86_64.tar.gz
cd yugabyte-2026.1.2.0-b137/
tar -xf node_agent-2026.1.2.0-b137-linux-amd64.tar.gz && cd 2026.1.2.0-b137/scripts/

    On ARM, extract node_agent-2026.1.2.0-b137-linux-arm64.tar.gz instead.

  2. Edit node-agent-provision.yaml in the scripts directory. The file is commented; see its defaults on GitHub. These are the options you typically change.

    Node settings

    OptionWhat to set
    yb_home_dirDirectory on the node where YugabyteDB is installed.
    yb_user_homeHome directory of the yugabyte user. Defaults to yb_home_dir. v2025.2.4.0 and later.
    chrony_serversAddresses of your NTP servers.
    yb_user_idUID for the yugabyte user. Use the same UID on every node for consistency.
    is_airgaptrue for airgapped installations.
    use_system_level_systemdDefaults to false, which uses user-level systemd.
    node_ipFQDN or IP address of this node, reachable from the other nodes.
    tmp_directoryDirectory for temporary files during provisioning.
    is_configure_clockboundInstalls ClockBound as a systemd unit to improve clock accuracy and reduce YSQL read-restart errors. Requires chrony. Universes created with the provider get time_source set to clockbound.

    YBA connection (lets the script create or update the provider)

    OptionWhat to set
    urlBase URL of your YBA instance.
    customer_uuidYour customer ID, shown under Profile > User Profile in YBA.
    api_keyAPI token from Profile > User Profile > Generate Key. The user needs the Admin role or higher.
    node_nameA name for the node.
    node_external_fqdnFQDN or IP address of the node, reachable from the YBA server.

    Provider details (the provider is created if it doesn’t exist)

    OptionWhat to set
    provider nameName of the new or existing provider to add the node to.
    region nameRegion of the node, for example us-west-1.
    zone nameZone of the node, for example us-west-1a.
    instance_type nameExisting instance type, or a name for a new one (for example c5.large).
    cores, memory_size, volume_sizeCores, memory (GB) and volume size (GB). Optional when using an existing instance type.
    mount_pointsData mount points, created before you run the script. Optional when using an existing instance type.

    The logging options (level, directory, file) control the provisioning log.

  3. Run the script as root or via sudo. It runs preflight checks, provisions the node (including ulimits and transparent hugepages), installs node agent, and creates the provider or adds the node to it. 
    sudo ./node-agent-provision.sh
  4. Reboot the node. If a preflight check failed, a reboot can also fix some issues, such as ulimit settings.
  5. Verify by opening https://<yba-host>/nodeagent. It lists the activated node agents and their status.

More options

Split provisioning between an OS team and a DB team

Both teams use the same package and configuration file. The OS team runs only the steps that need root: creating the yugabyte user, chrony, THP, ulimits, sysctl, sudoers and root systemd units.

sudo ./node-agent-provision.sh --root

The DB team then runs the user-scoped steps as the yugabyte user, with no sudo: user systemd, cgroups, node agent setup and registration with YBA.

./node-agent-provision.sh --noroot
Use one configuration file for many nodes

From v2025.2.4.0, keep one shared YAML and pass only per-node values with --config_override. Each value is JSON matching the field type, and nested fields use dotted paths such as yba.instance_type.name.

./node-agent-provision.sh \
    --config_override yba.node_external_fqdn=\"db-node-03.example.com\" \
    --config_override ynp.node_ip=\"10.1.2.3\" \
    --config_override yba.node_name=\"db-node-03\"
Reprovision nodes that are already in a provider

From v2025.2.4.0, --generate_config builds node-agent-provision-generated.yaml from YBA, given the YBA URL, API token and node FQDN or IP. Use --generate_and_run to generate the file and run with it:

./node-agent-provision.sh --generate_and_run --provision
./node-agent-provision.sh --generate_and_run --dry_run

See also Reprovision universe nodes.

Run only the preflight checks 
sudo ./node-agent-provision.sh --preflight_check

From v2025.2.4.0, --preflight_check_out_file saves the check results as JSON for automation.

Allow-list the script in sudoers

If your security policy requires listing the exact commands run under sudo, add these two:

sudo ./node-agent-provision.sh --preflight_check
sudo ./node-agent-provision.sh

To audit what the script will run, find the rendered templates from a preflight run and inspect them with cat. The first file is the precheck template and the second is the execution template; both vary by OS and YBA release.

sudo ./node-agent-provision.sh --preflight_check 2>&1 | grep "INFO - /tmp/tmp.*$"

Common questions

Which mode is “automatic”?

Both modes end with nodes that YBA manages automatically. The only difference is who performs OS-level provisioning: YBA (Privileged) or your administrator via the script (Unprivileged).

Does Unprivileged mean YBA can’t manage my universe?

No. After provisioning, YBA manages the universe through the node agent in both modes: creating universes, upgrades, scaling, backups, and so on.

What if I need to reprovision a node or apply OS changes later?

In Privileged mode, YBA performs them over SSH. In Unprivileged mode, your administrator re-runs node-agent-provision.sh on the node. See Reprovision nodes.
